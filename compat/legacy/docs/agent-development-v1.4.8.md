# Agent Protocol — continuous campaigns

This contract governs new execution using the accepted routing manifest. Historical
receipts keep their original schemas and validators. The operational engine,
lifecycle and campaign schemas are unchanged. The preceding accepted authority
qualifies every successor and every new path registration; a candidate never
selects its own authority, policy or required checks.

## One objective, one ledger, complete delivery

The actual user instruction establishes scope and authorization. A campaign links
the existing issue/PR ledgers of its authorized workstreams and derives its view
from them. Keep one writer per branch and one operational checkpoint per
workstream. An issue description, rendering or cache is not a second editable
authority. Do not seize PRODUCT owners or modify their checkpoint under PROTOCOL.
Perform only coordinated, indispensable synchronization on an owned PRODUCT
branch; otherwise deliver on the default and verify the supported resume route.

An authorized campaign continues through prerequisites, implementation, correction,
qualification, normal merge, post-merge verification, required effects and final
reconciliation. A Core merge, pilot or successful deployment is not completion of
a wider scope. Necessary Core and adapter corrections stay within existing
authorization. Additional repositories and PRODUCT releases require actual scope;
being mentioned in a registry grants none. Public Core development remains
clean-room: generalized requirements and synthetic fixtures only.

## Execution and loop control

Use the existing ledger to derive `execution-step` input, independently selected
by the host through `--trusted`. The projection is disposable, not a new lifecycle.
Its exact repository, operation, source head, input digest and event identify an
operation. Record useful progress as verified advancement, new evidence, a fixed
cause or a precisely identified dependency. The host must verify those meanings;
declaring a progress token or hashing it does not establish progress.

| State | Required behavior |
| --- | --- |
| CONTINUE_NOW | Execute the selected authorized step, including supported recovery, in this session. A generated prompt is not delivery. |
| WAIT_EXTERNAL | Retain the exact existing dependency, observation and bounded wake condition. Perform independent ready steps first. |
| HUMAN_ACTION_REQUIRED | Finish independent preparation; identify the actual rule/source, prepared result, exact material action and verified link. |
| TERMINAL | All scoped steps are verified complete. Reconcile once; do not invent another prompt or closure task. |

After two equivalent observations without useful progress, stop repeating the
operation. Classify the cause and select a supported recovery or precise external
dependency. An unchanged deterministic error stops after its first diagnosis.
A retry needs changed relevant conditions/inputs, a compatible cause and valid
authorization. Renaming an operation or changing an irrelevant digest is not a
recovery. The host verifies this semantic relationship before selecting a recovery.
Stopping repetition never skips a gate or abandons independent authorized work.

`execution-step` rejects an unresolved loop without a concrete recovery/dependency,
missing authorization without a concrete human action, unchanged recovery
coordinates and dependency cycles. It selects independently executable work before
an external wait. Its result is never push or merge qualification. Retain original
iteration observations in the same checkpoint, with evidence references rather
than complete repeated payloads. Unknown measurements remain null.

The existing `validate-wait` preserves an expired handle only to request a fresh
observation of that same run/attempt. Expiry cannot assert continued liveness,
success or authority. Do not poll equivalent states or rerun deterministic failures.
After a write with uncertain outcome, observe the existing object/receipt before
retrying. A platform denial ends that attempt; no equivalent retry until its cause
changes. Never promise background execution without an actual durable scheduler.

## Material continuity

Before suspension, environment change or handoff, persist the necessary bytes in
an authorized durable commit/branch or accessible artifact/bundle. Retain the base,
exact inventory, digests, minimal restoration instructions and adequate retention.
A scratch path, description, hash without bytes or upload intention is insufficient.
Use the existing recovery export/verify/restore commands. Fetch the saved artifact
independently of the original workspace and verify restoration into a fresh
directory, including byte inventories and any Git bundle prerequisites. Preserve
the durable identifier and successful restore receipt in the owner ledger.

Recovery grants no authority and refreshes no observation. Verify restored source
and dependency bytes and recollect required live gates. Missing material is an
explicit evidence gap. Reconstruction is a new delta requiring new qualification,
never recovery of unavailable originals. Record exhausted searches and repeat them
only when a new identifier, location or source supplies a concrete lead. Store only
necessary artifacts; exclude credentials and unrelated private material.

## Command, event and validator parity

Before adoption, exercise each consumer's actual public command, resulting delta,
real PR-event guard, collector, qualifier and unchanged native entrypoint. A local
FULL without `pull_request` context does not prove the PR-event guard. Preserve
event identity in evidence; post-merge, PR and trusted-base checks are distinct.

Updating resume metadata with an unchanged owner is not ownership transfer.
Never simulate a handoff by temporarily changing owner. A same-owner operation
must be expressly supported by the accepted lifecycle and real PR guard, or be
rejected before any checkpoint write. Preserve owner, binding, ancestry, immutable
coordinates and all historical commits. Recovery of an already rejected write
uses only a separately accepted, exact restoration command and verified history;
never manually repair checkpoint bytes, erase history or silence the guard.

Protocol changes follow existing normative change control and predecessor scope
qualification. Registration, adoption and use are separate. CI must execute the
same commands used locally. Keep full suites, coverage, isolation, supported
runtime and accepted limits; do not inflate timeouts or remove tests to pass.

## Accepted dependencies and evidence reuse

For PRODUCT using unchanged adopted dependencies, use the accepted-baseline
route where supported. The pin need not follow unrelated default-branch movement
in Core. Independently verify authority, immutable source, complete manifest,
helper bytes/modes, compatibility and required validity conditions. New adoption
verifies the selected accepted Core revision and its provenance through the
existing canonical route. Neither a candidate declaration nor an old pin alone
proves authority. Introduce no perpetual revocation service or remote check.

Acquire source scope-first: repository/default identity, authority and applicable
instructions, owner/checkpoint, relevant diff, then necessary files/dependencies.
Full materialization requires a concrete implementation dependency or native gate;
identity alone normally requires tree/blob metadata. Reuse verified bytes without
redelivering unchanged text to the model. Local byte verification and model text
delivery are separate costs. Context loss or uncertain provenance requires the
pertinent revalidation, not a claim that retained files remain in model context.

| Evidence | Reuse boundary |
| --- | --- |
| Immutable objects | Exact repository/object, original provenance and complete verified bytes/metadata. |
| Content-dependent checks | Same actual source, relevant dependencies, policy, validator, runtime and workflow. Existing non-reusable local checks still run. |
| Live observations | Refresh required PR, review/thread, default, authority and effect observations at the operation boundary. |

Record the specific invalidator: source, policy, runtime, workflow, artifact,
effects, audience or authorization. Invalidate affected dependents, not unrelated
evidence. Never rename a receipt to transfer PASS to another candidate. Final
qualification remains on the exact commit. A cached inventory digest does not
prove a mutable workspace; only an actually verified immutable source can anchor
reuse. Mutations, source ambiguity and context loss trigger relevant verification.

## Transport and capabilities

Inventory runtime/extensions, dependencies, filesystem semantics, Git, reads,
writes, workflow events and artifact transport before choosing a delivery path.
Use actual supported endpoints and entrypoints. Git branch paths preserve slash
separators while encoding each segment; retain exact branch and commit bindings.
Preserve raw tool responses outside source before normalization. Fail closed on
missing/partial blobs, unsupported schemas, incomplete pagination or reviews.

`connectorFailure` distinguishes explicit rate-limit evidence, access denial,
transient server failure, deterministic error and missing capability. HTTP 403
alone is not a rate limit. No classification retries automatically. Preserve the
actual error and relevant response metadata for diagnosis; do not fabricate old
protection fields, query rulesets unnecessarily, bypass authentication or limits,
or turn a missing diagnostic capability into inferred access.

## Qualification, effects and acceptance

Retain complete exact-head CI histories/attempts/jobs, required reviews, all current
findings/threads, ownership, path/effect binding, actual base/head ancestry and a
fresh expected head. Use the normal GitHub merge endpoint; platform protections
remain authoritative. An optional review in progress adds no gate, but any valid
finding remains actionable. Emojis and comments without verdicts are not approval.
The current trusted repository policy selects required PR/post-merge checks;
neither a candidate policy nor missing protection access can waive them.

Keep readiness, consent, execution and acceptance distinct. CI cannot establish
production configuration, populated data, deployment or acceptance. STAFF/cohort
is production audience; preserve server-side restrictions and shared effects.
Explicitly authorized deferred acceptance remains DEFERRED, bound to its exact
scope/candidate, never PASS or a blanket exception for future effects.
The `readiness` command retains DEFERRED only for VERIFICATION or CERTIFICATION,
with a separate host-trusted deferral receipt binding the complete release
identity, exact phase/elements, explicit authorization, ordered acceptance
sequence and validity period. Keep it unresolved; it grants no effect authority
and cannot certify delivery. Independently verified NOT_APPLICABLE prerequisites
count as satisfied while retaining that status; they never prove execution.

Use `readiness`, `authorization-reuse` and `recovery-plan` with independently
selected actual evidence. BEFORE_EFFECTS, PARTIAL, MONITORING_FAILED after completed
effects and UNKNOWN remain distinct. Diagnose failed smoke before selecting an
effect. Completed migrations/publications are not repeated because monitoring
failed. Reconcile unknown effects read-only first. No new production access is
created for diagnostics. Nondelegable immediate confirmations remain required at
their actual boundary, after all other authorized preparation is complete.

Protocol adoption has no application release by default. Determine deployment
applicability from actual changed paths and trusted workflow triggers. Record
DEPLOY_NOT_REQUIRED with the verified reason when no deployment is necessary.
Never trigger production merely to demonstrate a rollout or carry pending PRODUCT
changes into an automatic deployment. Protocol publication and application
release identity are separate contracts; publish only the required Protocol
identities/artifacts, never manufacture an application version bump.

## Idempotent campaign closure

Use existing closure tools and receipts; group compatible updates and retain
required CHECKPOINT_ONLY operations without creating redundant closure chains.
Do not migrate lifecycle or remove AGENT_STATUS authority in this revision. Never
put closing keywords in a PR when its referenced issue must remain open, including
negated sentences. Use neutral references and close only after real criteria pass;
observe the resulting state. Record late findings with origin/correction evidence.

`campaign-audit` uses the existing operational audit checks with an independently
selected exact authorized repository inventory. It binds that scope and campaign
reference and validates every integration, current gate, vendor byte/mode and
provenance. Omitted authorized consumers, duplicate rows and unresolved findings
fail. The historical five-repository audit is unchanged. The current campaign
qualifies Core and its three authorized executable consumers. Any authorized
Nexus registry reconciliation retains a separate descriptive receipt, without
executable-consumer qualification or authority. Update that registry once at
campaign closure.

Campaign completion requires the accepted Core, successful pilot, every authorized
consumer adoption and actual final verification, coherent routing/pins/adapters,
resolved Protocol blockers and preserved concurrent PRODUCT ownership/resume.
Report COMPLETE only for that entire scope. Otherwise report NOT_COMPLETE with
the precise retained dependency, durable material and one necessary next action.
Do not hand the user another prompt for already authorized executable work.

The retained operational/recovery procedures continue to apply. For editorial
delegation, load the [unchanged delegation procedure](agent-development-v1.4.7.md#editorial-delegation):
an independently selected, prior adopted policy, exact batch/check coverage and
actual grant remain necessary. Delegated automatic approval is never human review
or publication consent. Historical campaign/pilot restrictions are not new scope.
This contract supersedes older orchestration instructions requiring an out-of-scope
registry integration or an artificial next prompt after terminal completion.
Keep model recommendations and real metrics in the existing
checkpoint when an actual handoff is needed; no model change or extra authority
follows from a recommendation.
