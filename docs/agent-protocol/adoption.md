# Native adoption and migration

Select source repository, immutable revision, release inventory and provenance
through the accepted predecessor/local change-control. Verify canonical bytes,
Git/archive modes and source identity. Consumer copies are byte-identical vendor
dependencies; modify native adapters outside them. Do not create a local Core fork
or replace the product's own Core. Wrapper locations follow the native runtime.
The independently accepted local adapter profile selects the exact vendor directory;
the planner does not impose a metadata directory on every runtime. Git internals,
temporary caches and overlapping native wrappers are refused. A candidate cannot
change that directory by supplying a replacement profile with a recomputed digest.

Adoption requires the actual native entrypoints, collector, PR event guard,
qualifier and CI to exercise the same accepted engine and policy. Update operational
and Work pins, source acquisition, synchronization, manifests and host instructions
coherently. A changed pin or vendor copy alone does not complete adoption.

Classify each old status surface before migration. A non-authoritative cache stays
a cache and retains useful release/epic/slice context. An authoritative checkpoint
or legacy receipt keeps its schema, original validator, meaning and result. Active
owners remain on their supported legacy route until a coordinated operation is
qualified; do not manually edit checkpoints or assume their work. New workstreams
may use the accepted current lifecycle without reinterpreting historical receipts.

The adoption planner checks managed file ownership and preserves local edits,
unknown files and removed historical dependencies for explicit review. Cleanup
requires import/CLI/link/anchor/CI/packaging/sync/recovery and indirect-reference
checks, both rename sides, exact modes and case-insensitive collision checks.
An old version in a filename does not establish obsolescence. Keep tested shims
only for proven consumers, with a removal criterion. Do not delete unique evidence,
open-work material, tags, releases, errors or someone else's branch.

An offline audit is a derived view of local ledgers under an independently accepted
closed scope. It does not discover repositories or create global operational state.
Missing/blocked consumers remain in the denominator. Engine adoption, necessary
state migration, cleanup and native conformance are reported separately. Private
consumer observations stay in an authorized private location.
